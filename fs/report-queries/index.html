GUMBO Wave-1 construction + NEPA risk map for Josh (Fibersmith)

1. Pull the Wave-1 project rows sql
SELECT r.subgroup, r.project_name, r.state, r.county,
       r.households, r.households_to_be_built,
       r.total_miles, r.miles_complete, r.model_miles_to_build,
       r.build_start_date, r.build_end_date,
       m.field_status, m.field_status_source, m.contrac_status_live,
       m.ocius_project_id
FROM raw_household_detail_v4 r
JOIN v900_build_meta_v1 m
  ON m.version_tag = r.version_tag AND m.row_id = r.row_id
WHERE r.version_tag = ?
  AND LOWER(TRIM(COALESCE(r.include_status, ''))) = 'yes'
  AND m.wave_tag = 'wave1_tom_ben'
ORDER BY r.build_start_date, r.subgroup

Pulls every project row tagged wave_tag='wave1_tom_ben' that is Include=Yes, for one pinned model version. The JOIN to v900_build_meta_v1 is on version_tag + row_id -- a row-grain join, not a name match -- so field_status and ocius_project_id line up exactly with the plan row they belong to. model_miles_to_build is a straight passthrough here; nothing in this query does math on it. That's the number that shows up as 'mi' in the CSV.

2. NEPA overlap -- not SQL, a spatial join python
def nepa_join_for(tree: STRtree, geoms: list, meta: list[dict], poly) -> dict:
    approved_mi = 0.0
    blocked_mi = 0.0
    for idx in tree.query(poly):
        idx = int(idx)
        g = geoms[idx]
        if not poly.intersects(g):
            continue
        rec = meta[idx]
        if rec["approved"]:
            approved_mi += rec["mi"]
        else:
            blocked_mi += rec["mi"]
    ...

There's no SQL for the NEPA numbers -- it's a geometry operation. Each project's leftover polygon (after the parent/child dissolve) is tested against every NEPA route line using an STRtree spatial index: a fast bounding-box pre-filter (tree.query) followed by an exact intersects() check on the survivors. Every NEPA line that actually crosses the polygon adds its own Miles attribute to either the approved or blocked running total, depending on whether that NEPA package's ESAPTT status says Notice to Proceed Complete. That's nepa_approved_mi / nepa_blocked_mi in the CSV.

GUMBO UT box map (GIS ground truth)

https://thebourque.com/fs/ground-truth-map/

Parish/leftover polygons, marketing + SwyftLoc model-location dots, Contrac CA status

1. No SQL here -- counts are a lookup, not a live count python
def _counts(idx: dict[str, dict], *keys: str) -> tuple[int, int]:
    for key in keys:
        row = idx.get(key)
        if row:
            return int(row.get("marketing_n") or 0), int(row.get("swyftloc_n") or 0)
    return 0, 0

This map does not itself count marketing or SwyftLoc points inside a polygon. For every leftover shape it draws, it looks up marketing_n / swyftloc_n from data/ut_fsa_score/ut_fsa_score.json (built separately by scripts/report_ut_fsa_score.py) by matching the shape's own name or poly_id. The map is a drawing + lookup step, not the counting step.

2. UT1 formula (the box's density-match score) python
def ut_score(marketing_n: int, swyftloc_n: int) -> float | None:
    if swyftloc_n <= 0:
        return None
    return marketing_n / swyftloc_n

UT1 = marketing dots divided by SwyftLoc dots in the same box. Below 1 means the SwyftLoc (buildable) universe in that box is bigger than the marketing footprint -- thin take relative to what's there. swyftloc_n = 0 returns None ('n/a' on the map), not a divide-by-zero or a fake 0.

Wave / Contrac-adjusted remaining

https://thebourque.com/fs/wave-remaining/

Filterable project list (parish/wave/project, Include Yes+No) with plan vs Contrac-adjusted remaining miles/passings/BEAD and CSV export

1. Pull every project row for this model version sql
SELECT h.subgroup, h.project_name, TRIM(h.county) AS county, h.state,
       UPPER(TRIM(h.include_status)) AS include_status,
       h.total_miles, h.model_miles_to_build,
       h.households, h.households_to_be_built, h.bead_passing,
       h.build_start_date, h.build_end_date,
       m.wave_tag, m.flags_json, m.field_status, m.field_status_source,
       m.ocius_project_id
FROM raw_household_detail_v4 h
LEFT JOIN v900_build_meta_v1 m ON m.version_tag = h.version_tag AND m.row_id = h.row_id
WHERE h.version_tag = ?
  -- optional AND filters added here for parish / subgroup / include / wave
ORDER BY m.wave_tag, county, h.subgroup

Pulls every row for the pinned model version -- a LEFT JOIN, so a project with no build-meta match still comes through (that's how parent/off-grid rows and Include=No rows make it into this report, unlike the Wave-1 map's inner JOIN + hard-coded Include=Yes filter). Any parish/subgroup/Include/wave filters the operator picks get appended as extra AND clauses with '?' placeholders -- never string-concatenated raw values.

2. Batch-join live Contrac status sql
SELECT ocius_project_id, project_status, design_miles, miles_ml_built,
       perc_complete, design_locations
FROM contrack_roq_outcome_v1
WHERE ingest_batch_id = 'CONTRACK_OUTCOME' AND ocius_project_id IN (...)

A second query, run once with every ocius_project_id from step 1 batched into a single IN (...) -- not one query per project. ingest_batch_id pins it to the one stable, fully-finished ingest job, so a half-completed re-ingest can never leak partial rows into this report.

3. The mainline/non-mainline split itself (Python, not SQL) python
if c and status == "complete":
    mi_remain_adj = max(0.0, total_mi - miles_ml_built)
    hh_remain_adj = 0.0
elif c and status == "in construction":
    pct = perc_complete / 100.0
    # Mainline (miles) is allowed to move early via the Contrac ROQ overlay.
    mi_remain_adj = max(0.0, total_mi - miles_ml_built)
    # Households/BEAD are non-mainline ("Access") -- frozen at plan until
    # Contrac reports Complete. perc_complete is a MILEAGE completion signal,
    # not a passings/CPE/drop signal -- it must never scale households.
    hh_remain_adj = hh_remain_plan
else:
    mi_remain_adj = mi_remain_plan
    hh_remain_adj = hh_remain_plan

Three cases, checked in order. Contrac says Complete -> 0 households remaining (miles remaining = plan miles minus whatever Contrac's own miles_ml_built recorded, floored at 0 so a slightly-stale plan number can't go negative). Contrac says In Construction -> miles remaining gets the same ROQ-overlay treatment as Complete (mainline is explicitly allowed to move early, core_rules_plan_field_remainder), but households remaining is left at the plan value, unchanged -- non-mainline categories are frozen until Contrac reports the job fully Complete, and Contrac's perc_complete is a mileage-build percentage, not a households/passings completion signal. No Contrac ROQ job at all (a parent row, or a project not yet in the field system) -> the Contrac-adjusted column is simply set equal to the plan column, unchanged, for both miles and households. (2026-08-18: this replaced an earlier version that wrongly scaled households by perc_complete in the In Construction branch -- a real canon violation, fixed same day.)

2. Labor/material atomic pricing resolution (two separate bugs, both fixed 2026-08-18 pt9) python
# Bug #1 -- pricing source (src/contrack_gumbo_buckets.py): OPS_DRAFT_V900 has
# zero rows of its own in tbl_atomic_labor/materials/arrays. Canary-check the
# labor table before pricing any template with this version's tag; fall back
# to the Williams-825 pin instead of silently pricing at $0. tbl_mst_bom_dollar
# has never had a Williams-825 row either -- it gets its own permanent Ver8.2.1
# footnote pin via the sibling resolve_mst_bom_version_tag().
def resolve_atomic_pricing_version_tag(cursor, version_tag):
    if _version_has_atomic_rows(cursor, version_tag):
        return version_tag, False
    return ATOMIC_AUTHORITY_PIN_VERSION_TAG, True  # Williams-825

# Bug #2 -- labor/material split (found only after #1 was fixed): most
# _add_bucket(...) call sites in template_mainline_bucket_breakdown() only
# ever passed per_mile=, so BucketAmount.labor/.material stayed ~$0 on every
# job even once pricing was real. Fix: expose the labor-vs-material

ug_mi, ug_lab, ug_mat, ug_ok = conduit_ug_per_mile_labor_material_split(rules, array_unit, ...)
_add_bucket(buckets, "mainline_conduit", per_mile=ug_mi, labor=ug_lab, material=ug_mat, ...)

# Then, per mainline bucket, in _remainder_mainline_bucket() (plan_field_remainder.py):
labor_share = (plan_labor / plan_sub) if plan_sub > 0 else 0.0
material_share = (plan_material / plan_sub) if plan_sub > 0 else 0.0
unsplit_share = max(0.0, 1.0 - labor_share - material_share)
remain_labor_cost = remain_cost * labor_share
remain_material_cost = remain_cost * material_share
remain_unsplit_cost = remain_cost * unsplit_share

core_rules_atomic_units_authority names two independent bugs found the same day (TECH_NOTES 2026-08-18 pt7 then pt9), not one. Bug #1 (pricing source): before pulling any atomic labor/materials/arrays row, resolve_atomic_pricing_version_tag() checks whether this model version has its own rows in tbl_atomic_labor; if not (true for OPS_DRAFT_V900 today), every atomic lookup for that template falls back to the Williams-825 pin (ATOMIC_AUTHORITY_PIN_VERSION_TAG) instead of silently returning $0 -- tbl_mst_bom_dollar gets the same treatment from a separate function, resolve_mst_bom_version_tag(), pinned to its own Ver8.2.1 footnote tag since it has never had a Williams-825 row. Bug #2 (labor/material split), only surfaced after #1 shipped and the report was re-run: labor_remain_cost was still near-$0 on every job, because most bucket-population call sites in template_mainline_bucket_breakdown() were only passing the combined per_mile total, not the labor/material components underneath it -- conduit_ug_per_mile_labor_material_split() (src/conduit_ug.py), legacy_handhole_labor_material_split() (src/handhole_qty.py), and _array_pair_split() (src/contrack_gumbo_buckets.py, splice/terminal/aerial arrays) now expose those components so every mainline bucket (conduit, fiber, aerial, handhole, terminal, splice, other/catch-all, embedded) carries a real labor + material split. _remainder_mainline_bucket() (src/plan_field_remainder.py) then divides each bucket's own remain_cost by that specific bucket's own plan labor-vs-material tag -- not a portfolio-wide ratio -- and reports any untagged residual (e.g. the magic-mile rollup trueup, mainline_embedded, which carries no labor/material tag at the Inputs grain at all) as remain_unsplit_cost rather than inventing a split.

3. NEPA + BEAD RC spatial joins (Python, not SQL) python
nepa = w1mod.nepa_join_for(nepa_tree, nepa_geoms, nepa_meta, leftover_polygon)
rc = rc_join_for(rc_tree, rc_geoms, rc_meta, leftover_polygon)

Two STRtree spatial joins against the same project leftover polygon (parent/child dissolve already applied): one against NEPA route lines (reused verbatim from the Wave-1 + NEPA risk map's own join function), one against BEAD give-back Reason-Code points. A project's full Contrac-adjusted remaining passings count as 'at risk' the moment any non-clear NEPA line touches its footprint -- this is a binary flag on the row's own remaining passings, not a fraction of the NEPA line's own length.
