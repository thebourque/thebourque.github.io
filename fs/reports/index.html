GUMBO Wave-1 construction + NEPA risk map for Josh (Fibersmith)

Last regenerated: 2026-08-18 18:05 UTC (6.6 hr ago)

How it was generated

  • Model: OPS_DRAFT_V900. Pulls Include=Yes rows tagged wave_tag='wave1_tom_ben' from raw_household_detail_v4 joined to v900_build_meta_v1 (field_status, contrac_status_live, ocius_project_id).
  • Each project is bucketed into one of 4 cohorts by field_status + build_start_date: pre-2026 still active, 2026 in construction, 2026 not started, or scheduled start.
  • Each project is matched to its leftover polygon from the live ArcGIS ProjectAreas export (parent/child dissolve already applied -- children carved out of parent CDA/DA/AG shapes).
  • That leftover polygon is spatially joined (STRtree) against a NEPA route-line index built from ESAPTT + NEPARoutes, summing approved vs. unapproved (blocked) line-miles that geographically intersect the project footprint. This produces nepa_status (clear / partial / blocked / no_data) and the approved/blocked mile totals.
  • 'mi' in the CSV is the raw plan value (model_miles_to_build straight from the HouseholdData workbook's own 'Model Miles to Build' column) -- it is NOT Contrac-adjusted.
  • Static snapshot: re-run scripts/_dump_wave1_josh_map.py to refresh, then rebuild+redeploy the hub site.

  • Sharing Wave-1 construction status with Josh (Fibersmith) and other external stakeholders.
  • Identifying which Wave-1 projects have geographic overlap with unapproved/blocked NEPA review corridors, so they can be flagged or escalated before construction reaches them.
  • Browsing Wave-1 remaining plan miles by cohort (pre-2026 active / 2026 in construction / 2026 not started / scheduled).

✗ Not for

  • Contrac-adjusted (field-prorated) remaining miles or passings -- 'mi' here is plan-only. Use the Wave / Contrac-adjusted remaining report for the field-adjusted figure on the same projects.

Last regenerated: 2026-08-19 00:31 UTC (8 min ago) · 1,036 rows

How it was generated

  • Model: OPS_DRAFT_V900. Pulls every project row (Include=Yes AND No, all waves) from raw_household_detail_v4 joined to v900_build_meta_v1.
  • For each project, joins live field status from contrack_roq_outcome_v1 on ocius_project_id (version-independent -- always current, not tied to a specific model run's refresh).
  • Plan remaining = households_to_be_built / model_miles_to_build, straight from the model's own plan-vs-field remainder engine.
  • Contrac-adjusted remaining overlays that live field status, and mainline (miles) is NOT treated the same as non-mainline (households/BEAD) -- core_rules_plan_field_remainder only lets mainline move early: Contrac Complete -> miles = plan minus Contrac's own miles_ml_built (floored at 0), households/BEAD = 0 (display-only; does not rewrite the plan value); Contrac In Construction -> miles get the same ROQ-overlay adjustment as Complete, but households/BEAD stay FROZEN at the plan value (perc_complete is a mainline-mileage completion percentage, not a passings/CPE/drop signal, and canon forbids moving a non-mainline category from partial field data during construction); no Contrac ROQ job (parent/off-grid row) -> plan value unchanged for both.
  • 2026-08-18 bugfix: a prior version of this report prorated households/BEAD by perc_complete during In Construction, which silently violated core_rules_plan_field_remainder (non-mainline must stay frozen until Complete). Fixed same day -- see docs/textbook/TECH_NOTES.md 2026-08-18 and src/wave_contrac_remaining.py module docstring.
  • BEAD remaining (plan and Contrac-adjusted) is bead_passing scaled by the same remaining-share ratio as households.
  • All 1,036+ rows are embedded inline in the page as JSON; every filter (parish/wave/project/Include), rollup, and the CSV export run entirely in the browser -- no server, nothing sent anywhere.
  • Static snapshot: re-run scripts/gen_wave_contrac_remaining_page.py to refresh, then rebuild+redeploy the hub site.

✓ Intended uses

  • Parish/wave/project-level plan-vs-field remaining comparison for miles, passings, and BEAD in one place.
  • Identifying which projects Contrac shows further along (or fully complete) than the raw plan number implies.
  • Ad-hoc CSV pulls for a specific parish or project set (e.g. the St. Landry Parish cut sent to Josh Richardson 2026-08-18).

How it was generated

Pulls Include=Yes, wave_tag='wave1_tom_ben' rows with hh_remain_adj > 0 (Contrac-adjusted passings remaining) from the same engine as the Wave/Contrac-remaining report (src/wave_contrac_remaining.py) -- miles/passings/BEAD remaining, Contrac-adjusted the same three-case way: Complete -> miles get the ROQ-overlay adjustment, households/BEAD -> 0 (display-only); In Construction -> miles get the same ROQ-overlay adjustment (mainline is allowed to move early), households/BEAD stay frozen at the plan value (core_rules_plan_field_remainder -- non-mainline categories do not move on partial field data, and perc_complete is a mileage signal, not a passings signal); no ROQ job -> plan value unchanged for both. Pricing resolves to this model version's own atomic tables when present, else falls back to the Williams-825 authority pin (OPS_WILLIAMS_V825_RETIME) -- src/contrack_gumbo_buckets.resolve_atomic_pricing_version_tag() -- never a silent $0. tbl_mst_bom_dollar has its own permanent footnote pin (Ver8.2.1). Buckets with no labor/material tag at the Inputs grain (chiefly the magic-mile rollup trueup bucket) are reported separately as unsplit_remain_cost rather than guessed into either side -- labor_remain_cost + material_remain_cost + unsplit_remain_cost always foots to mainline_remain_cost. Every row names its labor_remain_source (matched_williams825_pin / matched_own_version / no_ocius_job_match).
